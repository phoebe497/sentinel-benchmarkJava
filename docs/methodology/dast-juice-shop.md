# DAST over OWASP Juice Shop

The SAST corpus (BenchmarkJava) measures how accurately the agent judges
findings, because it ships ground truth. It cannot do anything else: it is
source code, and the rules forbid deploying it. Everything from step 4 of the
final flow onwards - propose a probe, get it approved, send it through the
gateway, filter the response - needs a **running** application with real
endpoints. That is what this pipeline adds.

## The stack

```
        ┌──────────────── edge (published) ────────────────┐
        │   localhost:8080  ->  gateway                    │
        └──────────────────────┬───────────────────────────┘
                               │  allowlist + rate limit + timeout
        ┌──────────────────────┴──── internal: true ───────┐
        │   juice-shop:3000        demo-api:8000           │
        │   (DAST subject)         (guardrail lab)         │
        │        ▲                                         │
        │        └── zap (profile: scan, passive baseline)  │
        └──────────────────────────────────────────────────┘
```

Neither upstream publishes a port. The topology *is* the proof: any request
that reached Juice Shop from outside the network necessarily passed the
allowlist in [`configs/gateway-policy.yml`](../../configs/gateway-policy.yml).

ZAP is the one exception, and it is deliberate. It sits on the internal network
and scans Juice Shop directly, because a scanner is not the agent - it plays the
same role Semgrep plays when it reads BenchmarkJava source. The agent's request
tool never gets that path; it knows one address, the gateway.

## Why the baseline scan, not a full scan

`zap-baseline.py` spiders the app and reports only what ordinary traffic
reveals. It sends no attack payloads. A full scan (`zap-full-scan.py`) is an
active attack and is out of scope for this project.

Juice Shop is an Angular SPA, so the traditional spider alone only sees static
assets. The AJAX spider (`-j`) drives a headless browser, which makes the app
issue the same XHR calls a user would - that is how `/rest/...` and `/api/...`
responses enter the scan at all, and those are exactly the endpoints the agent
can later probe.

## What comes out

| | |
| :--- | :--- |
| Raw output | `artifacts/week-6/dast/zap-baseline.json` (+ HTML report) |
| Provenance | `artifacts/week-6/dast/manifest.json`, generated by `scripts/security/zap_dast.py` |
| Normalized | the shared observation schema, via `normalizer.normalize_file` |
| Grouped | `EndpointGroup`, one group per (endpoint, issue) |

The manifest is derived from the artifact, never hand-written, so it cannot
drift from the evidence it describes: scanner version and image digest, target
image digest, the exact command, the output's SHA-256, and the counts.

## Two decisions worth knowing

**One group is one issue on one endpoint, not every issue on one endpoint.**
A single endpoint routinely carries unrelated alerts - a missing CSP header and
a leaked private IP, say. Merging them would force one verdict onto two
different findings, so the group key is (endpoint path, reported CWE, alert
title). Numeric path segments collapse to `{id}` so the endpoint lines up with
the `{id}` wildcards the gateway publishes.

**`EndpointGroup` has no `expected_cwe` field.** BenchmarkJava has ground truth;
a running app does not. The DAST group carries only `reported_cwes` - what the
scanner claimed - so no downstream code can quietly treat a scanner claim as a
verified fact. A test asserts the field's absence. Precision/Recall on this
branch is an LLM-as-judge proxy (Grok 4.5), stored after the run under
`artifacts/week-6/evaluation/verdict-metrics-*-judge.json`.

## Non-determinism, stated up front

The spider explores a live SPA, so the alert set changes between runs. Tests
therefore assert *behaviour* against a small inline fixture and *provenance*
against the committed artifact - never alert counts. Reported numbers always
name the run they came from.

## Reproduce

```bash
git submodule update --init --recursive
bash scripts/stack.sh up        # gateway + juice-shop + demo-api
bash scripts/stack.sh scan      # ZAP baseline -> artifacts/week-6/dast/
bash scripts/stack.sh routes    # the allowlist the gateway publishes
python -m sentinel_benchmark.indexer
bash scripts/stack.sh down
```

## Coverage of the current run

The run recorded in the manifest produced 9 alert types over 18 URLs, which
normalize to 33 observations in 18 endpoint groups. Only some of those
endpoints are in the allowlist: `/`, `/sitemap.xml`, `/ftp`, `/robots.txt` and
`/rest/admin/application-configuration` are probe-able, while `/styles.css`,
`/socket.io/` and `/ftp/*.bak` are not. That gap is intentional - when the agent
meets a finding it cannot reach, the correct output is "cannot verify", and the
gateway returns `403` if anything tries anyway.

The most useful finding for the end-to-end flow is **Private IP Disclosure
(CWE-497) on `/rest/admin/application-configuration`**: it is body-observable,
the endpoint is allowlisted, and whether a private IP in a config response is a
real vulnerability is a genuine judgement call rather than a lookup.
